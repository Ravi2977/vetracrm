The most common reason software projects disappoint is not bad coding. It's unclear requirements. A few pages written in plain language can save weeks of rework.

1. Goal: why are you building this?

Write two or three sentences on the problem and the outcome. Example: "Reduce order processing time from 2 days to same-day, and give the owner a live view of pending dispatches."

2. Users

List each type of user, what they do, and roughly how many there are: sales staff, warehouse staff, accounts, managers, customers, dealers.

3. Current workflow

Describe how work happens today, step by step, including the Excel sheets, WhatsApp groups and paper forms used. Attach samples.

4. Desired workflow

Describe how it should work with the new software. Use simple user stories:

  • "As a salesperson, I want to create an order from a quotation so I don't retype items."
  • "As the owner, I want a daily summary on WhatsApp of orders, dispatches and collections."

5. Must-have vs nice-to-have

Split features into must-have for the first version and later improvements. This keeps the first phase focused and affordable.

6. Reports and documents

List the reports, invoices, labels and printouts needed, with sample formats.

7. Integrations

Which systems must it connect to? Tally, website, payment gateway, WhatsApp, devices?

8. Platforms and access

Web, mobile, desktop? Offline needs? Access from outside the office?

9. Data and migration

What existing data must be moved, from where, and how much?

10. Acceptance criteria

How will you know it's done? Example: "An order can be created, approved, invoiced and dispatched, with stock updated, in a test run with real data."

Template

Goal · Users · Current workflow · Desired workflow · Must-have features · Later features · Reports · Integrations · Platforms · Data · Acceptance criteria. Ten headings, a few lines each.
